## 1. mybatis-spring-boot-starter 3.0.5 与 Spring Boot 4.x 不兼容

### 现象
应用启动失败,错误信息看起来像缺 mapper bean:
```
No qualifying bean of type 'com.tmt.TMLibrary.mapper.BookMapper' available
```

### 第一层根因(让人误判的方向)
看起来像"`@MapperScan` 没启用"或"`@Mapper` 没被识别"。**这个判断是错的**。

### 第二层根因(真正的原因)
`mybatis-spring-boot-starter 3.0.5`(2024-11 最新版,之后再无更新)内部:
1. `MybatisAutoConfiguration` 标注了 `@AutoConfigureAfter(org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration.class)`
2. `MybatisProperties.CoreConfiguration.applyTo()` 内部调用 `PropertyMapper.alwaysApplyingWhenNonNull()`

Spring Boot 4.x 把这两个东西都改了:
- `DataSourceAutoConfiguration` 从 `org.springframework.boot.autoconfigure.jdbc` 搬到了 `org.springframework.boot.jdbc.autoconfigure`
- `PropertyMapper.alwaysApplyingWhenNonNull()` 被移除

结果:`MybatisAutoConfiguration` 加载条件静默失败,自动配置被跳过。

### 修复
**手写 `MyBatisConfig.java`**,绕开 spring-boot-starter:

```java
@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(MybatisProperties.class)
public class MyBatisConfig {
    @Bean
    public SqlSessionFactory sqlSessionFactory(DataSource dataSource, MybatisProperties properties) throws Exception {
        SqlSessionFactoryBean factoryBean = new SqlSessionFactoryBean();
        factoryBean.setDataSource(dataSource);
        factoryBean.setMapperLocations(properties.resolveMapperLocations());
        factoryBean.setTypeAliasesPackage(properties.getTypeAliasesPackage());
        // 不要调 properties.getConfiguration().applyTo(...),
        // 它内部用了 SB 4.x 已删除的 API
        return factoryBean.getObject();
    }

    @Bean
    public MapperScannerConfigurer mapperScannerConfigurer() {
        MapperScannerConfigurer configurer = new MapperScannerConfigurer();
        configurer.setBasePackage("com.tmt.TMLibrary.mapper");
        return configurer;
    }
}
```

### 怎么提前发现
- 项目里用了**很新的 Spring Boot(4.x)+Java(21+)** 组合 + **老的 Spring 生态库**(没跟进新版本的),**强烈怀疑兼容性**
- 启动报"找不到 X bean"类错误,**先用 `--debug` 看 auto-config 报告**(`./mvnw spring-boot:run -Dspring-boot.run.arguments="--debug"`),看对应 `AutoConfiguration` 的 "Did not match" 段
- `javap -v` 看依赖的 jar 里某个类的 `@AutoConfigureAfter` 注解,**看它引用的类在当前 SB 版本里是否存在**

### 怎么避免
- **优先选 SB 版本对应的 spring-boot-starter** —— MyBatis 这种"周边"库的发布周期往往跟不上 SB 主版本
- 项目选 SB 4.x 时,**先确认所有 starter 都已发布兼容版本**,否则会埋雷

## 2. BookMapper.xml:XML 声明不在第 1 行

### 现象
MyBatis 加载 mapper XML 时报:
```
SAXParseException: lineNumber: 5; columnNumber: 6;
The processing instruction target matching "[xX][mM][lL]" is not allowed.
```

### 根因
XML 1.0 规范硬性规定:`<?xml version="1.0" encoding="UTF-8"?>` 必须在文件**最开头**,**前面不能有任何东西**(连注释、空行都不行)。

我们项目的 mapper 文件结构:
```
第1-3行:中文注释
第4行:空行
第5行:<?xml ?>     ← 不合法!
```

### 修复
把 `<?xml ?>` 挪到第 1 行,注释挪到声明后面。

### 怎么提前发现
- 任何 XML 文件,**第 1 个非空字符必须是 `<?xml`**(或直接是根元素)
- 用 `head -c 30 file.xml | xxd` 看前几字节,如果不是 `3c 3f 78 6d 6c`(`<?xml`),就是问题

### 怎么避免
- 写 XML 文件时,**先把声明写在最前面**,再加注释
- 一些 IDE(比如 IntelliJ IDEA)对 XML 声明位置有视觉提示;`xxd` 或 `hexdump` 是最快的命令行验证手段

## 3. MyBatis SQL 里的 `<=` `>=` 撞 XML 解析

### 现象
mapper XML 通过前一个检查后,启动时再次报 SAX 解析错误:
```
SAXParseException; lineNumber: 142; columnNumber: 65;
The content of elements must consist of well-formed character data or markup.
```

### 根因
SQL 里有:
```xml
<select id="selectListByPriceRange">
    SELECT ... WHERE price >= #{minPrice} AND price <= #{maxPrice}
</select>
```

`<=` 和 `>=` 中的 `<` 在 XML 里是**特殊字符**,必须转义为 `&lt;` 或放进 `<![CDATA[...]]>`,否则 XML 解析器以为这是新标签的开始。

### 修复
**用 CDATA 包整段 SQL**(推荐,干净):
```xml
<select id="selectListByPriceRange">
    <![CDATA[
    SELECT ... WHERE price >= #{minPrice} AND price <= #{maxPrice}
    ]]>
</select>
```

或者**逐个字符转义**:
```xml
WHERE price &gt;= #{minPrice} AND price &lt;= #{maxPrice}
```

### 怎么提前发现
- SQL 里有任何 `<` `>` `&` 字符,都需要 CDATA 或转义
- MyBatis 写完后**先 `mvn test` 或 `mvn spring-boot:run` 一下**,XML 解析错误比运行时报错早得多
- 表里所有 `<` 字符:
  ```bash
  grep -n '<[^!?]' src/main/resources/mapper/*.xml
  # 排除正常标签 <select> <if> 等
  ```

### 怎么避免
- **写 SQL 条件时,脑子里要有 XML 字符转义这根弦**
- MyBatis 推荐做法:动态 SQL 用 `<if>` 标签;静态 SQL 含特殊字符用 CDATA
- 范围查询的写法也可以避免:`BETWEEN #{min} AND #{max}` 不含 `<`

## 4. @Configuration 代理机制 + MapperScannerConfigurer 启动顺序

### 现象
启动日志里有 WARN:
```
Cannot enhance @Configuration bean definition 'myBatisConfig' since its singleton instance has been created too early.
The typical cause is a non-static @Bean method with a BeanDefinitionRegistryPostProcessor return type
```

### 根因
`MapperScannerConfigurer` 实现了 `BeanDefinitionRegistryPostProcessor`(在 bean 真正实例化**之前**就要跑),而 Spring 的 `@Configuration` 默认会**代理 @Bean 方法**,先创建配置类实例再调用 @Bean 方法。这与 `BeanDefinitionRegistryPostProcessor` 的"必须最先跑"语义冲突。

### 修复
在 `@Configuration` 注解上加 `proxyBeanMethods = false`:
```java
@Configuration(proxyBeanMethods = false)
public class MyBatisConfig { ... }
```

或把 @Bean 方法改成 `static`。

### 怎么提前发现
- 任何返回 `BeanDefinitionRegistryPostProcessor` / `BeanFactoryPostProcessor` 的 @Bean 方法,都要考虑顺序问题
- Spring 启动 WARN 出现 "singleton instance has been created too early" 几乎都是这个

## 5. Maven "Nothing to compile" 但实际编译失败的陷阱

### 现象
我加了新文件后,`./mvnw compile` 输出:
```
Nothing to compile - all classes are up to date.
BUILD SUCCESS
```

但实际上**新文件编译失败了**,target/classes 里的 .class 文件里有 **"Unresolved compilation problems"** 字符串。Spring 启动时调用这些 .class 就崩。

### 根因
Maven 用**文件 mtime** 判断是否需要重新编译。新文件如果跟某个旧文件 mtime 相同,可能被错误地认为 "up to date"。

### 修复
- 编译错误时**强制重新编译**:`./mvnw clean compile` 或 `./mvnw compile -U`(强制更新)
- 检查生成的 .class:`javap -v target/classes/path/to/Class.class | grep "Unresolved"`,看是否有 "Unresolved compilation problems"
- **保险做法**:每次新文件加完后,显式 `rm -f target/classes/<新文件>.class` 再编译

### 怎么提前发现
- 启动报错,但 `mvn compile` 不报错
- 看 `target/classes/` 下的 .class 文件,如果包含 `"Unresolved compilation problems"` 字符串就是这种情况
- 用 `javap -v <class>` 确认类是否正常编译

## 6. "完成"≠"验证":P0 阶段为什么没暴露这些 bug

### 问题描述
P0 阶段我们勾掉了所有任务,以为"完成"。但实际上:
- 应用的 7 个 handler **一个都没真跑过**(因为启动根本起不来)
- 启动失败是另外一个 bug(MyBatis 配置),掩盖了 P0 是否真的生效

### 教训

> **完成 ≠ 验证**。勾掉 checkbox 前,必须实际验证它工作。

具体执行清单:
- 改完代码 → **必须** `./mvnw spring-boot:run` 启动看 log
- 加新接口/handler → **必须** `curl` 或 `httpie` 真的打一次
- 加单测 → **必须** `mvn test` 跑过看绿
- 改配置 → **必须** 重启确认生效

### 写测试的真正价值

今天如果 P0 阶段有哪怕一个 `@SpringBootTest` 跑通,**所有 4 个 bug 会一次性暴露**:
- 启动失败(版本兼容)
- MyBatis XML 解析失败(声明位置 + CDATA)
- @Configuration 代理顺序

**集成测试比手动 curl 验证可靠得多** —— 它每次代码改动都强制跑一遍。

## 7. 常见 Spring Boot 启动错误的诊断路径

### 步骤 1:看 ApplicationContext 初始化日志
```bash
./mvnw spring-boot:run 2>&1 | tail -100
```

### 步骤 2:用 `--debug` 看 auto-config 报告
```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments="--debug" 2>&1 | grep -A2 "MybatisAutoConfiguration\|DataSourceAutoConfiguration"
```

找:
- `XxxxAutoConfiguration: Did not match` —— 这个 auto-config 没加载
- `XxxxAutoConfiguration matched` —— 加载了
- 跟在 "Did not match" 后的条件(`@ConditionalOnClass did not find ...`)是真正的根因

### 步骤 3:看 Caused by 链
错误日志里的 `Caused by` 是关键。**最后一个 Caused by 才是真正的根因**:
```
Caused by: org.springframework.beans.factory.BeanCreationException: ...
Caused by: java.lang.IllegalArgumentException: Property 'sqlSessionFactory' required  ← 真正原因
Caused by: org.springframework.beans.factory.NoSuchBeanDefinitionException
```

### 步骤 4:看依赖树确认 jar 都在 classpath
```bash
./mvnw dependency:tree | grep -i "mybatis\|spring-boot\|jackson"
```

### 步骤 5:确认 env vars 真传到了 Spring
- 用 `@Value` 注入到一个临时 @Component,在 log 里打印
- 或设 `-Dspring-boot.run.jvmArguments="-DDEBUG=true"` 通过 JVM 属性传

### 步骤 6:用 javap 看编译产物
```bash
javap -v target/classes/com/foo/Bar.class | grep -E "RuntimeVisibleAnnotations|Unresolved"
```

### 步骤 7:看实际 JAR 里的内容
```bash
unzip -l ~/.m2/repository/org/mybatis/mybatis-spring/3.0.5/mybatis-spring-3.0.5.jar
# 看某个类在不在、它在哪个包里
```

## 8. 总结:5 条开发纪律

1. **跑过才能算完成** —— 改完代码 + 启动 + curl 三步走,任何一步没真做就不要勾 checkbox
2. **XML 字符转义不能忘** —— SQL 里 `<` `>` `&` 必须 CDATA 或 `&lt;` `&gt;` `&amp;`
3. **看错误要看根因** —— 不要停在第一个错误信息,顺着 `Caused by` 链往下挖
4. **新 SB + 老第三方库 = 高危** —— 用之前先看 starter 是否已发新版适配
5. **不要光推断,要执行验证** —— 涉及 Spring auto-config / 反射 / 类加载的判断,实际跑一下才知道
